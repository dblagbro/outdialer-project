# PostgreSQL 16 security release

The Outdialer and translation databases are upgrading from PostgreSQL 16.14 / Alpine 3.24.1 to the official PostgreSQL 16.15 / Alpine 3.24.4 image, pinned to `postgres@sha256:ac838714b7d794185a866e5a6b479b954e7d8a070568aa0acac6fe07c3070bf5` (linux/amd64). The primary Docker config digest is `sha256:4278d7b1e3deb3193ddc803158f6532963f059fc25a2eefaee4b5a9e71741873`; identical root filesystem layers and the registry manifest bind it to the peer-scanned image. Original image `sha256:e684c11a6c7c127c1b7602063cc6a13db0a12b62dfd770d83936c089751d498d` remains available for rollback.

At source review, the candidate is tested but **not deployed**. Consult the deployment receipt/DEPLOYED.md for subsequent rollout evidence. Preparation, source merge and production deployment are separate states.

The [16.15 release notes](https://www.postgresql.org/docs/release/16.15/) describe SQL security and correctness fixes and conditional migration steps. Both live clusters have only plpgsql, no logical replication slots or extra tablespaces, and unchanged libc collation metadata. The checks found no applicable extension reindex or custom output-plugin step. This stays within the existing PostgreSQL and Alpine major versions.

Online physical backups of both complete clusters were independently SHA256-verified on NAS, checked with pg_verifybackup (including WAL), and booted with both original and candidate binaries in containers with network=none. Schema and row fingerprints matched for all non-template databases. Synthetic transaction rollback, candidate restart durability and original-binary rollback preserving candidate-written data passed. The deployed Outdialer psycopg driver connected to the restored candidate through isolated loopback. No production restart or application write occurred during rehearsal. Private backup contents and configuration are excluded from Git.

The candidate scan has 1 Critical / 25 High matches, versus 1 / 37 for the original. All remaining candidate matches refer to Go stdlib in gosu1.19; no Alpine Critical/High match remained in this scan. The [gosu security policy](https://github.com/tianon/gosu/blob/1.19/SECURITY.md) requires checking used functionality. Its vendor-pinned govulncheck v1.1.4 examined the actual shipped binary. The crypto/tls symbols implicated by [GO-2026-4337 / CVE-2025-68121](https://pkg.go.dev/vuln/GO-2026-4337) were not reported present. This limits applicability; raw scanner totals remain unchanged.

The same symbol check also found the Medium [CVE-2026-61801](https://github.com/moby/sys/security/advisories/GHSA-mjcv-p78q-w5fw) in moby/sys/user0.1.0 (fixed0.4.1), involving excessive memory use when parsing attacker-controlled user/group files. This is a residual finding, separate from the High/Critical-only scan. Both containers use the image's root-owned account files, with no mounted passwd/group inputs and the server running as postgres. No remote route to supplying those files was established. Binary symbols alone do not prove an exploitable call path. Keep this finding visible pending an upstream gosu dependency release; do not rebuild an unsupported variant merely to hide version matches.

`deploy_pg16.py --preflight-only` validates the real root Compose, live environment, concrete volumes, memory/OOM settings and launch behavior. Sixteen configuration regression checks cover scoped edits, concurrent changes, type normalization and inherited image defaults. The operator requires a merged/check-passed source receipt with hashes, a completed rehearsal and the shared capacity guard. Before each sequential rollout it stops only that database's two application clients, verifies no other database client remains, takes a new physical backup with independent NAS verification, and boots that exact backup on the candidate. It then recreates only the database through the existing root Compose and resumes the original application containers after checks. No added Compose file, broad stack down, database-major migration or production backup restore is used.

On failure, restore the original image against the **current** data volume, whose binary rollback was rehearsed. Never overwrite accepted writes with an older snapshot automatically. Retain all original volumes, images, private backups and NAS copies. Run new capacity-intensive work only through the maintained storage/capacity_guard.py, reserving at least64GiB. Do not rerun an operator whose receipt already exists without reviewing its state.

The root Compose image pins, Outdialer project Compose and translation root-Compose installer must use the same immutable reference. Translation has no Git remote; its narrow patch is mirrored here rather than uploading unrelated history. Asterisk, DevinGPT and AVIS remain disabled. Real calls, providers and IPv6 are outside this database acceptance test.
